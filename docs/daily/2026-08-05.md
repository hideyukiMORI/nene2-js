## 🔴 1.3.0: 「(a) が (b) になる」を実行前に検出

- **触った物**: `release/1.3.0`（`3dac48c` 起点＝`./testing` 上陸の直前）・`package.json` 1.3.0・CHANGELOG。
- **問題**: `./testing` は既に main に merge 済み〔#124 / #126〕。**main を 1.3.0 として publish すると `./testing` も出る**〔実測: main の `exports` = `['.', './testing', './package.json']`・`src/testing` 8ファイル〕。版番号が 1.3.0 でも艦に届く物は (b) と同一になり、裁定の意味が消え、1.4.0 に出す物が無くなる。
- **★教訓**: **版の付け替えではなく切り出し点の問題だった。** 「版を上げる」と「何が入るか」を同一視すると、**裁定どおりに操作した結果が裁定と違う物になる**。前日の「無料で緑」（seam 無しで必須4項目が素通り）と同じ構造で、**実行前に測るかどうか**だけが分かれ目。
- **裏取り**〔実測〕: リリース枝の `exports` = `['.', './package.json']`・`src/testing` 不在・`npm run check` 緑・599 tests。**publish dry-run success**（run 30926130161）で tarball を直読し **`dist/testing` = 0件／陽性対照 `dist/transport` = 48件**。陽性対照を置いたのは、grep が壊れていても 0 件になるため。
- hub 裁定で形式承認（リリース枝から publish・main へは merge しない・main には CHANGELOG のみ後追い）＋条件2つ。

## 🔴 publish が生んだ齟齬を同乗で潰した

- **触った物**: README / SECURITY の「Opting out (**available in the next minor release**)」→「**since 1.3.0**」。
- **★教訓（恒久化した）**: **版名の扱いは publish の前後で反転する。**
  - publish 前 = 版番号を名乗らない（07-18 裁定「未 publish の版番号を公開 docs で主張しない」）
  - publish 後 = **名乗る**（「次の minor で」は publish した瞬間に嘘になり、1.3.0 の利用者は自分に来ているか判断できない）
- 片側だけ守ると必ず腐るので、**リリース手順に grep を入れた**（`next minor release` 等を洗い出し、release PR か follow-up で消す）。hub が fleet へ共有（tokens / standards / i18n も同じ publish 手順を持つため同型が起きる）。

## リリース手順の恒久化（`docs/development/releases.md`）

hub 指示で2件を手順書へ:

1. **版名の反転**（上記・grep つき）
