## P2-2 本題: `./testing` 契約テストの配布（Issue #123）

- **触った物**: `src/testing/`（新設7ファイル）・`package.json` の `exports` に `./testing`・`tools/smoke-pack.mjs`・`docs/howto/transport-contract.md`（新設）・README「Transport contract for consumers」節・CHANGELOG `[Unreleased]`。
- **設計正本**: [fleet #232](https://github.com/hideyukiMORI/nene2-fleet-tooling/issues/232)（hub 検収 PASS）。work order は `_work/handoff-nene2js-l2-contract-testing-2026-08-05-work-order.md`。
- **問題の実体**: 統一UT は `tests/` にあり `files` の外。公開済み 1.2.0 の `exports` も `['.', './package.json']` のみ〔実測・`npm view`〕。fleet は各艦の `node_modules` を直読して **test 0本**を確認済み。保証されていたのは「パッケージが壊れていない」であって「艦の統合が契約どおり」ではない。
- **形**: **L-a**（`expect*` = 呼ぶと assert する部品・i18n `expectCatalogParity` と同型）＋ **L-b**（`runTransportContract(deps)` = describe/it を登録）の2層。L-b が本体 —— **ランナー結果に現れて初めて「実行された / skip 0」を機械で見られる**。
- **契約項目**: 5群 **12必須**（C1 ミラー4 / C2 token 保管3 / C3 401・403 3 / C4 再取得2）＋ C5 任意1。44ケースからの絞り込み基準は「**艦が供給する値で壊れうるか**」。内部実装の検査は配らない（毎回緑＝測っていない）。
- **空振りガード**: 登録 0 でも「想定より少ない」でも fail。差異は `exemptions`（`reason` + `ref` 必須＝AU-2 形）として受け取り**明示的に差し引く**。理由か参照が欠けた exemption は**拒否**する。ガード自体を `assertContractCoverage()` として切り出し**直接テスト**した（緑の suite 越しにしか到達できないガードは、それ自身が無防備）。
- **版の可視化**: 実行時に `[nene2-client/testing] transport contract v1.2.0 · <product> — N registered, M exempted` を1行出す＋ `result.version`。**古い契約でも新しい契約でも見た目は同じ緑**なので、版が出ていなければ版ずれは永久に見えない（fleet 実測: 11艦中10艦が 1.1.0 のまま）。版定数は package.json と一致することをテストで強制。
- **裏取り**〔実測〕:
  - `npm run check` 全段グリーン。テスト **650 passed**（skip 28 = 従来からの live smoke）。契約まわりの新規は **48本**。
  - **12項目すべて「わざと壊すと赤」を実証**（推論なし）。各ケースに対応する破壊ノブを持つ参照 fixture を作り、`TransportContractError` の `caseId` とメッセージまで断言。
  - `pack:smoke` を拡張し、**インストール済み tarball から `./testing` を import** して解決を確認（`files` の境界は repo 内テストでは見えない —— 今回の穴そのもの）。
- **★教訓（設計が1回ひっくり返った点）**: fleet 原案の `runTransportContract({ client: apiClient })` は**成立しない**。transport は生成時に `fetch` を束縛する（#105）ため、**組み立て済みの client は観測できない**。そこで deps は「艦の**配線**」（config / tokenStore / hooks）を受け取る形にし、アダプタを持つ艦のために `createTransport` seam を残した。これで「アダプタが1経路だけ transport を迂回している」という**パッケージ内テストでは原理的に見えない事故**が見える。
- **★教訓（負テストが設計を直した）**: C1-2 の負テストを書こうとして、**当初の deps 形では破壊のしようがない**と分かった。「壊せない項目は、項目の選定か API 形のどちらかが間違っている」という hub の指摘どおりで、`createTransport` seam を足す判断はここから出た。推論で済ませていれば気付かなかった。
